# Playground layout and program view

The user approved a compact workbench with stable execution controls, Code/Program/Inspect views on phones, and code/program beside an inspector on desktop. The Program view must connect current source to the complete program and actual emitted instructions. Supplied initialisation, capture/reporting and exit remain expandable; user code, labels, functions and data remain visible. Full programs use source unchanged. Fragments and C functions use makeProgram's real supplied assembly. C has no source-line mapping from TinyCC. Registers are actual observations, with pinned and changed entries easy to find and all registers accessible.

Checked implementation facts: makeProgram owns source composition and lineOffset; builder disassembles the actual ELF and returns user instructions and all instructions. Instrumented fragments stop stepping at the reporting checkpoint. Raw programs can finish without a final state report; the existing last-pause qualification must remain visible. Editing stops active execution and retains the prior build/observations; those need an explicit stale label. Source projections must use composition metadata from makeProgram, never parse user text for invented boundaries. View switching must retain DOM/editor, selection, CPU, scroll and keyboard focus; mobile must keep a stable workspace height. Theme, fullscreen reparenting, import/project switching and lesson transfers remain supported.

Implementation is restricted to this repository. Follow docs/course-authoring.md and imported prose instructions. Use a separate drafting pass and independent learner/technical reviews. Test real generated source reconstruction, ELF instructions/PC, pseudo-instruction expansion, C/full programs, stale edits, switching/reset, mobile/desktop themes and fullscreen. Run appropriate shared regression checks and distinguish local, CI and published verification.

## Implementation and independent review

`makeProgram` now returns exact source sections in addition to its unchanged assembled source and line offset. The read-only Program projection retains their order, with supplied initialisation and capture/reporting/exit folded. User labels, functions and data stay in their original source span. Raw programs have one unfolded exact source span. C is shown as its own source file alongside the supplied assembly caller. Machine instructions come from the actual build, with scopes that distinguish the compiled `lesson` function from all executable instructions. Build/stale-source and C mapping qualifications stay outside the scrolling listing. The scope toolbar remains reachable, and the PC follows within the listing's own scroller.

The standalone layout retains the same editor and inspector DOM behind Code/Program/Inspect views. Desktop keeps the inspector beside the left pane. Execution controls occupy stable space, setup is a project menu, and pins/changed comparisons surface relevant observations without removing access to all registers. Code following on the standalone page scrolls only CodeMirror. Native and fallback fullscreen retain inner scroll offsets. Pinning is a view-only action available during a run; keyboard focus survives its rerender, including when a filter hides the unpinned row.

The separate drafting record is `playground-layout-copy.md`; canonical strings are in `content/guides/playground.json`. Independent learner and technical findings, corrections, exact probes and limits are in the two review records. Their accepted findings covered pin focus/discoverability, visible PC following, phone page scrolling, C instruction scope, fullscreen inner scrolling and pin availability during execution. Final targeted rechecks also covered the sticky toolbar and stationary stale/C qualifications. No reviewed findings remain open. These are Chromium checks, not physical-device validation or a novice study.
