# Playground layout technical review

Independent review of `feat/playground-program-view`, against `docs/playground-layout-brief.md`, `docs/course-authoring.md`, the imported authoring rules, and the actual generator, builder, debugger and worker. The reviewer did not write the implementation. The preview was served from this working tree at `http://127.0.0.1:4220/playground/`. Working-tree changes made during review are distinguished below.

## Findings

1. **P2, resolved: C instruction scope needs an exact label.** `Your instructions` initially selected only the compiled `lesson` symbol's range. A real C function calling a separately defined `helper` ran successfully; the selected range showed 16 instructions, while All showed 177 including supplied code and the helper. The original C note, “These are its compiled instructions”, did not distinguish those scopes. Direction: name the `lesson` function in the selected scope and say that All includes compiled C and supplied assembly. The corrected generated copy and actual scope behavior passed the final recheck below.
2. **P2, resolved: Program scroll is lost when entering fallback fullscreen.** With Supplied initialisation expanded, `#program-source-view.scrollTop` was 150. After `Expand workspace`, the same element reported 0; Escape retained 0. The selected Program view and the expanded fold survived. The root moves through a hidden dialog, which can discard internal scroll offsets. Direction: retain and restore the workspace's inner scrollers around reparenting, in both directions. The correction passed native and fallback rechecks below.
3. **P2, minor, resolved: enabled pin controls silently do nothing while running.** During an actual infinite-loop run, `Pin t0` had `disabled: false` and `aria-pressed: false`. Clicking it left the same values. `controller.togglePin` returned while the debugger was locked. Direction: disable the controls while they are unavailable, or permit this view-only operation during a run. The implementation now permits the view-only operation and passed the running-loop recheck below.

The brief initially said that an edit preserved a paused CPU. The actual existing `onSourceChange` stops active execution. A probe that tried Continue after an edit timed out on the correctly disabled button. The brief was corrected to distinguish a stopped run's retained observation from a continuing CPU. This is a correction to the stated contract and reviewer probe, not evidence of successful continuation.

The initial full-program machine listing used `allInstructions`, which omits source-line metadata. The author changed it to the actual full `disassembly` before the raw-program probe; that probe saw nine instructions, nine actual source labels and one PC mark. Omitting a source association would be an incomplete view, rather than an invented association.

## Checked behavior

- Compared the new model against `main` for 24 combinations: assembly fragments, C and complete programs; xv6 and Linux generation; empty source, missing terminal newline, ordinary assembly and user labels/data/comments containing reserved-looking label text. In every combination the emitted assembly and `lineOffset` matched `main`, and concatenating all generated sections reconstructed the assembly exactly. The command made 72 assertions. Its initial console label incorrectly said 48 variants; the count here reflects the loop actually run.
- Real GNU assembly and xv6 stepping of `li t0, 0x123456789abcdef` produced eight instructions for that source line. The Program listing showed the actual `lui`, `addiw`, shifts and adds; one step advanced PC from `0x100a0` to `0x100a4` and the sampled t0 was 598016. Editing to a smaller constant retained that prior listing with the explicit stale-build note. It did not pass off the new source as the old executable.
- A failed build of `badinstruction` retained the three-instruction previous successful listing and showed the stale-build note. Diagnostics and Error remained available. This did not establish successful execution of the edited source.
- On a 390 × 844 touch viewport, repeated Program, Inspect and Code selections retained the paused PC, one selected workspace tab and focus on that tab. In the measured sequence, page scroll stayed 97, workspace height stayed 540.15625 and workspace viewport top stayed 339.4375. These are observed browser geometry values, not fixed product requirements.
- Program-source inner scroll survived Code/Program switching, source/machine-mode switching and mobile Inspect/Program switching at 150. Expanded source sections remained expanded.
- The Pinned register filter initially showed t2. Pinning t0 added it. After the first real instruction, Changed showed t0; switching signed/unsigned reading preserved that comparison. Pin state and the full 32-register set remained available.
- The working-tree pin-focus fix was observed: pressing Enter on `Pin t0` left focus on its replacement `Unpin t0` button.
- Native fullscreen on the touch viewport preserved the instruction PC, contained the width at 390 and returned with the same PC. Desktop fallback fullscreen retained the split panes, selected view and expanded source; its scroll-offset failure is listed above.
- Desktop workspace arrow-key selection moved the selected tab and focus to Program. The phone workspace exposed Code, Program and Inspect, while the desktop inspector remained beside the left pane.
- Complete Hello World source appeared unchanged in a single user block, with no supplied-code folds. Its actual full-program build produced the nine instruction/source associations and PC mark noted above. The C example compiled and executed a real helper call; the C function source was separate from the supplied assembly, without invented C-line associations.

## Final correction rechecks

- Reloaded the regenerated page and compiled the two-function C example again. The user-range option read `lesson function`, with 16 instructions and “This scope shows the compiled lesson function.” All showed 177 instructions and “All includes compiled C and the supplied assembly.” Both notes retained the no-C-source-line-mappings qualification.
- At 1280 × 900 with native fullscreen explicitly disabled, entering fallback fullscreen preserved Program source scrollTop 150. Scrolling there to 250 and leaving preserved 250 in the normal workspace. At 390 × 844 with native fullscreen enabled, entering and leaving likewise preserved 150 and 250. These were asserted after the corrected layout settled; both paths passed.
- Executed a real infinite loop, waited for Running, then clicked `Pin t0`. The button became `Unpin t0` with `aria-pressed=true`, while the machine remained Running. Stopping the run remained available.
- After the final refinement moved build/C qualifications outside the listing scroller and made scope/Jump to PC sticky, reloaded and stepped the C project at 1440 × 1000 and 390 × 844. Selected All and scrolled the listing to its end (observed scrollTop 4471 and 4675). At both widths, the last-build note, correct All/C qualification and Jump to PC control remained in the viewport. Jump to PC brought the actual marked instruction at `0x10250` into view. Editing the C function, returning to Program and scrolling to the end retained the explicit stale-source note, C qualification and control in view. These were browser assertions against the final arrangement, not source-only checks.

No findings remain unresolved in this reviewed scope.

## Limits

This pass used actual Chromium, GNU/TinyCC and xv6 in a local preview. It did not establish GitHub CI, deployment, physical mobile browser behavior, a novice study or every possible GNU assembler directive. Independent learner/theme checks and the parent's full regression suite are separate evidence. No implementation files were edited by this reviewer. Later implementation changes that affect the checked behavior require a corresponding recheck.
