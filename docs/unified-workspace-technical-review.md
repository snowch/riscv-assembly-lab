# Independent technical review: unified workspace

Copyright © 2026 Christopher Snow.

Reviewed the implementation independently from the actual shared controller, layout, project store, generated lesson integration and browser behaviour. The learner can read simple C and binary numbers; assembly notation, hexadecimal and calling conventions are introduced by the course. The review scope is real execution and state preservation when optional tools and personal projects share the lesson editor. It does not establish learning effectiveness or physical-device compatibility.

## Findings and rechecks

- **Blocker, lesson mount:** project metadata initially wrote `#project-kind`, which only existed in the standalone introduction. The access is now guarded. Fresh addition lessons mount and enable project controls without a page exception.
- **Blocker, lesson project handoff:** the lesson snapshot handler initially tried to pass a personal project through `fromLesson`, whose provenance requires a real lesson title and slug. The handler now distinguishes project contexts. Ordinary lesson project copying, subsequent edits and return to the lesson completed without page errors.
- **Blocker, clipped project actions:** the absolute actions menu extended beyond the clipped workbench, so the next lesson paragraph intercepted Save a copy. The dock now exposes project actions in its usable layout. The same ordinary pointer interaction passed on recheck; the original failure and an intermediate force-click probe are distinct from this passing recheck.
- **High, cross-context deletion:** a broad batch-control reset re-enabled Delete project while the lesson draft was active. That could remove the library's previously active project. The deletion handler now rejects lesson mode, and batch disabling preserves the previous disabled state. After creating a copy, returning to the lesson and running actual code, Delete project remains disabled and the saved copy remains listed.
- **High, project switching during case checks:** a context switch during Check all cases could invalidate the mutable lesson/case loop. Project switching and setup actions are locked during the batch; `loadProject` also rejects a batch-time switch. An overlap probe found Save a copy disabled and could not perform the switch. The guard was not bypassed to claim a successful switch.
- **Medium, lesson restoration labels:** restoring an original lesson context initially used an absent `sourceName` and project-specific source labels. The filename fallback and curriculum labels are restored. A selected exercise case returned with `lesson.s`, Restore starter, the exact source, the same prepared inputs and the original selected case.
- **Medium, unapplied setup:** source snapshot refresh originally rewrote setup fields on every source edit. Refresh now depends on context/activity/fixture identity. An unapplied `t0 = 81`, `t1 = 4` draft survived a Program-tab visit and a source edit. Applying it created an independent project; `add t2, t0, t1` actually ran with result 85. Return to lesson and reload retained the edited lesson source.
- **Simple initial state:** standalone initial project loading initially opened the optional dock through the controller's inspection selection. The standalone manager now closes the dock after its initial load.

The smaller project-mode context and early-lesson hex-reading observations were also corrected and independently rechecked. The legacy lesson handoff and the lesson-specific C-intent comparison are hidden while an independent project is active. Returning to the lesson restores both. Advanced register rows show real hex readings even in the addition lesson; the compact lesson observation remains focused on the relevant registers. Project copies, deletion, Undo delete and Return to lesson preserve the selected Projects tool, so their status and recovery controls remain visible. The page heading identifies the current project and restores the lesson title on return.

## Independent execution evidence

Probes ran against the actual local site and its existing GNU/TinyCC/xv6 worker path, not the earlier interactive mock.

- Standalone assembly finished with t2 = 12. A newly created C-function project compiled with TinyCC, linked, ran and finished with a0 = 12. One earlier C probe reached Error without retained diagnostics; repeating the same flow with diagnostics capture passed. That unexplained initial observation is recorded separately and is not represented as a confirmed product defect or a passing run.
- On a 390-pixel touch viewport, the complete Hello World example printed `Hello, RISC-V!`. Its ordinary run did not invent a final register report: the t2 reading remained unobserved. Starting machine stepping paused at an actual PC/source mapping. The Program view contained nine machine rows and one current-instruction marker while the editable source remained visible. Stack inspection showed eight observed doublewords; Memory showed 64 bytes. No page error occurred.
- The same phone probe selected the actual dark theme and measured document width equal to viewport width (390 pixels).
- A selected addition exercise case was copied, edited independently and restored. The exercise source and prepared input text matched their prior values, and the selected case remained “A zero input”.
- A custom-setup project executed a different result from the original lesson without being treated as an original-example failure. The lesson draft and saved project both remained available after returning and reloading.
- A final independent recheck at 390 and 1440 pixels ran the addition example and verified the visible advanced t2 hex reading. It then copied the compare-values lesson, checked the project heading and hidden lesson-specific resources, deleted and restored the copy through the still-selected Projects tool, and returned to the original lesson heading and resources. Both widths passed without page errors. No confirmed review finding remains unresolved in this reviewed scope.
