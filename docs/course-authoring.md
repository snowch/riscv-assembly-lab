## Course contract

Author one JSON array per assigned file under `content/`. Each object has:

- `id`: unique kebab-case URL slug, `module`: assigned module id, `title`, `summary` (one concrete sentence), `objectives` (1–3).
- `before`: 2–4 short paragraphs. Define new terms and instructions before use. Identify starting values and the moment observed. Inline backticks are supported. No HTML, no Markdown headings or fenced code blocks in paragraphs.
- `starter`: focused runnable assembly fragment. Usually 3–12 lines, more when a loop or function needs it. The lab supplies entry, reporting and exit. Branch to a local end label to skip helper functions. `lesson_data` names an aligned 64-byte memory region supplied below the editor. Do not define `_start` or `_lab_*` labels. Avoid a final `ret` in a top-level fragment: it has no ordinary caller. Function examples call their own helper and jump over its body.
- `observe`: 2–5 relevant architectural register aliases, e.g. `["t0","t1","t2"]` or `["a0","s0","sp","ra"]`. The CPU captures real values after the fragment; it preserves the original `sp` in the snapshot. Only list registers the learner has met. `result`: one of those registers, highlighted as the requested result.
- `inputs`: optional register map for initial example state, values as decimal/hex strings. All ordinary integer working registers start at zero unless listed. `sp` remains the xv6-provided 16-byte-aligned stack pointer. `gp`/`tp` are not teaching scratch registers. Show any supplied initial values visibly. Prefer loading example constants in the editable fragment in early lessons.
- `data`: optional array of 0–64 bytes (numbers 0–255), padded to 64. `memory`: optional `"data"` or `"stack"` selects a real 64-byte memory view. Data base is `lesson_data`; stack view begins at the fragment's final original sp. `memoryLabels`: optional `[ {"offset":0,"label":"first sample"} ]`, offsets in bytes. Use explicit little-endian bytes for multi-byte values.
- `prediction`: `{ "prompt": "What does t2 hold after these lines?", "register":"t2", "reading":"signed"|"unsigned"|"hex", "hint":"..." }`. Checked against actual execution, never a typed expected answer. Default signed reading.
- `explanation`: 2–4 paragraphs explaining why the mechanism produces the observation, plus the important edge or a plausible mistake. Do not merely repeat the intro. Do not state a prediction answer before the learner runs.
- `experiment`: `{ "task":"A fresh change to try", "hint":"Specific mechanism-based help" }`.
- `challenge`: `{ "task":"What to write, where inputs arrive, where the result must be, preservation requirements", "starter":"incomplete code", "reference":"working code", "hints":[three ordered hints], "cases":[...] }`.
- Each challenge case: `{ "name":"clear case label", "inputs":{"t0":"7","t1":"5"}, "data":[optional bytes], "expect":{"t2":"12"}, "memoryExpect":{"0":42} }`. Cases run on fresh actual xv6 guests, using the same learner code. Use at least three cases with a useful boundary. Omit memoryExpect if irrelevant. Expected register values compare 64-bit patterns, so decimal negatives and hex work. Do not test preservation of caller-saved registers across a function call unless the fragment explicitly saves them. References must pass every case; incomplete starters must fail at least one.
- `c`: optional short C intent alongside hand-written assembly, explicitly labelled as equivalent intent rather than compiler output. No invented source-line association or compiler-output claim.
- `language`: default `"asm"`. C lessons use `"c"` and define a complete, small `long lesson(long a, long b)` or `unsigned long lesson(unsigned long a, unsigned long b)` function. No host headers, libc, main, or inline assembly. The real browser TinyCC compiler produces an object, GNU ld links it with supplied assembly calling `lesson` with a0/a1, and the CPU reports a0 afterwards. `inputs`/case inputs supply a0/a1. Observe a0 as the result. Only rely on well-defined C for expected cases. Any unsigned C arithmetic uses unsigned types explicitly. TCC is the actual compiler; do not call its output GCC or infer optimisation behaviour. Actual compiler disassembly will be available as a disclosure.
- `references`: array of source keys: `integer`, `rv64`, `multiply`, `abi`, `assembler`, `xv6`, `c`.
- `sourceLessons`: related Assembly Lab lesson slugs for provenance.
- `originalityNote`: one sentence describing the teaching purpose of the adapted example and any architecture-specific redesign.

## Checked facts and style

The learner can read simple C (variables, if, loops, functions and arrays) and small binary numbers. No prior assembly, hexadecimal, two's complement or pointers. Introduce those where needed. Direct British English; use 'you'; no marketing, em dashes or ten-section padding. Keep a lesson around 250–450 useful words excluding code. Explain instruction notation (destination, immediate, offsets, labels) before asking for it. Use the source course's trip-computer situations when they help: ticks, sensor bytes, warnings, distance, fuel, arrays and bounded labels. One fresh exercise applies the mechanism rather than repeating the worked values.

RISC-V RV64GC: x0/zero always reads zero; t0–t6 are temporary registers. Registers are 64 bits. W operations sign-extend a 32-bit result. lw sign-extends, lwu zero-extends; lb/lbu and lh/lhu make the same distinction. No NZCV flags: derive carry with sltu and overflow with explicit sign comparisons. Arithmetic wraps to XLEN; signed C overflow is undefined. Conditional branches compare two registers directly. Register shift counts use low six bits (five for W operations). Base RV64GC has no rotate, shifted add, bit-clear or conditional-select instruction. li, la, mv, j, call and ret are pseudo-instructions, and source lines can expand to several machine instructions. Do not assume a four-byte instruction length when compressed instructions are enabled.

ABI: a0–a7 integer arguments, a0/a1 results; s0–s11 preserved; ra caller-saved. Standard stack alignment stays 16 bytes. Ret selects the next instruction address, not the result register. A nested call must save its own incoming ra. Stack release does not erase bytes. Standard RV64 narrow integer arguments extend to 32 bits by type, then sign-extend to XLEN, including canonical uint32_t arguments; do not teach all unsigned arguments as zero-extended.

M extension: div by zero returns all ones; rem returns dividend. Signed minimum / -1 returns the minimum; remainder zero. Arithmetic right shift of negatives rounds down, signed division truncates towards zero. Misalignment behaviour depends on environment; use aligned teaching data. xv6 write=16 and exit=2, not Linux syscall numbers. xv6 user programs have no raw device access. Current guest does not enable FPU context; optional floating-point material may teach bit representations using integer memory operations, never pretend native FP instructions execute.

Official checked text is at `/tmp/riscv-audit-{rv32,rv64,m,abi}.txt`; original sources: riscv/riscv-isa-manual and riscv-non-isa/riscv-elf-psabi-doc. Parent will validate every starter and reference using actual GNU assembly and CPU execution and obtain independent reviews. Authors should flag uncertainty rather than invent a semantic claim.
