## Findings, fixes and independent verification

1. **Medium: project-management chrome hides the initial source.** The first view stacks “Projects”, “Example”, a separate “Project name”, “Starting setup”, “Project”, execution controls and “Starting inputs” before the editor. At 1440×1000 the source editor starts at 712.8 pixels; at 390×1000 it starts at 1158.8 pixels, below the first viewport. The editing surface should be the main activity of this independent tool. Direction: move secondary name/example actions into compact management controls, avoid repeating the project context and fold setup guidance into the existing setup disclosure. Keep the lesson view unchanged. Screenshots `/tmp/playground-learner-390-light.png` and `/tmp/playground-learner-1440-dark.png`. **Corrected and rechecked:** secondary examples and rename actions now sit behind disclosures; repeated project/setup rows are removed. After the main density correction, the editor began at 456.2 pixels at 1440 width, 506.6 pixels at 800 and 725.1 pixels at 390, in both themes. A final phone-only heading/padding adjustment reduced the 390-pixel editor top to 709.8 pixels; this was independently measured again at viewport heights 844 and 1000. The initial code is visible in the phone viewport and the desktop workspace reads as the main activity. No further density finding remains.
2. **Medium: fullscreen drops the standalone layout.** “Full screen” reparents the workbench outside `.playground-shell`, which scopes its special layout. At 1440×1000 the workspace grows from 700 to 1654.6 pixels; register values change from 12.8-pixel compact grid rows to 25.6-pixel blocks. The separator occupies the generic two-column grid's right cell and the inspector drops below the source, leaving a blank right pane. Direction: put the standalone layout identity on an element that remains with the workbench and cover native and fallback fullscreen. Screenshot `/tmp/playground-learner-fullscreen.png`. **Corrected and rechecked:** a persistent workbench class retains the standalone three-column layout and compact register grid. Native fullscreen now keeps the workspace at 700 pixels high with 12.8-pixel register values and the inspector beside the source. Eight native/fallback × phone/desktop × light/dark combinations preserved the actual paused source and PC on entry/exit. Desktop keyboard divider resizing passed in each applicable combination.
3. **Medium: complete-program help contradicts the selected project type.** Complete-program source help says “Define _start and include your program’s exit code”, but “How this lab works” says “The lab supplies entry, reporting and exit code.” The runtime uses the complete source without that scaffolding. Direction: make shared help and the complete-source resource descriptor conditional on the source type. **Corrected and rechecked:** the full-program helper now says that the program defines its own entry, initialisation, data and exit. Its complete-source descriptor is “Your complete source, unchanged”. The visible source guidance still defines `_start`. Shared resize help also names the actual standalone pane controls, without promising the hidden lesson-only Expand editor action.
4. **Medium: the last-pause qualification is hidden when Memory is selected.** After pausing a complete program at entry, selecting Memory and continuing to exit, the register note warns that its readings are not exit values. That note is hidden in the Registers tab. Memory still says “Data bytes observed at …” while the toolbar says “Program finished”, without a visible observation moment. Direction: place the last-observation qualification above the inspector or in each affected view. The probe's memory sample was unreadable; this finding does not assert an incorrect numerical memory value. Screenshot `/tmp/playground-learner-full-program-memory-after.png`. **Corrected and rechecked:** a shared observation note remains visible across Memory, Stack, Registers and Debugger after a complete program exits. It names the last pause and warns that the values are not exit-register observations. A real paused/continued full program verified this on the phone layout; there were no page errors.

## Browser checks completed

Used the built app at local port 4250 with headless Chromium through Playwright. Initial matrix: 390, 800 and 1440 pixels, each in actual light and dark themes. Body colours were `rgb(245, 249, 248)` and `rgb(16, 30, 28)`. All six combinations had no document overflow or page errors, 32 register rows and no prediction/exercise/completion DOM. Setup application, New project dialog opening/Escape/focus recovery, and calculator conversion/arithmetic worked.

A separate 390-pixel touch-context probe paused an actual custom assembly fragment. An invalid reserved-register setup and malformed JSON import each left the source, paused PC and machine state unchanged. Continuing the real code produced the independently expected observation. Naming and reloading a saved project recovered the exact source. The addition lesson's current exercise code and selected case setup opened in a new tab; the lesson stayed paused with identical source and PC. The playground and the original lesson then ran independently. No challenge answer is included in this record.

At desktop width, a C example compiled and ran through the actual engine. The complete Hello World example produced console text, retained unobserved registers as dashes until a pause, showed eight actual stack rows, and qualified its retained register observation after continuing to process exit. Keyboard resizing changed the editor-width separator value without editing source. The fullscreen finding above was observed during this check. No browser page errors occurred.

## Terms and prior knowledge

The tool defines an assembly fragment, supplied scaffolding, `_start`, C function arguments/results, starting-register assignments, hexadecimal bytes and the distinction between saved source/setup and a running machine in its optional help. RV64GC, GNU, TinyCC, ELF and xv6 remain environment/tool identifiers; a reader need not understand them to run the initial fragment. The independent app is not a substitute for the course's instruction teaching. Complete assembly programs and low-level watches require instruction/address knowledge introduced by the course or brought by the reader. The fuller optional environment explanation distinguishes xv6 calls and current limitations.

## Limits and final status

All four findings have been corrected and independently rechecked. The final six-combination layout/theme matrix passed with no overflow or page errors, and the corrected phone/light, desktop/dark and fullscreen screenshots were visually inspected. Root-owned full-suite/unit/corpus results are not claimed here. Chromium was used; Safari, Firefox, physical mobile keyboards and screen-reader speech were not exercised. Private probes used browser evaluation only to inspect state/geometry; source edits and actions used the actual visible controls. The first final-verification script completed its eight fullscreen cases, then failed an overly specific private assertion requiring `_start` inside the shared helper paragraph. The corrected helper accurately describes owned entry code, while `_start` is already defined in the visible source guidance. A focused rerun checked both locations and the observation note on all four inspector tabs and passed. This was a probe expectation correction, not a product failure; the initial failure and corrected rerun remain separate outcomes.

No unresolved learner or UX findings remain within the checked scope.
